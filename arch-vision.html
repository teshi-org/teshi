3 差距分析：有什么 vs. 缺什么
维度 圣杯要求 teshi 现状 状态
感知层 DOM 编号注入 / AOM 无障碍树 → 结构化快照 CDP 可获取 DOM & Accessibility tree，已支持 snapshot ● 就绪

语义抽象化 Playwright 代码 → Gherkin + step defs + 索引注册 teshi 本身就是 Gherkin 编辑器，天然可做此输出 ● 就绪
沙箱约束 URL 白名单、最大步数、脏数据隔离 无任何沙箱机制 ● 不存在
幻觉断言防御 截图 + DOM 双重验证，独立复核 Agent 无验证机制 ● 不存在

4 ⚡ 必须防范的三个致命地雷

💥 状态爆炸 · 爱丽丝梦游仙境效应

现象：Agent 点到了退出登录、外部链接 → 从被测页面跳到了 Twitter → 在推特页面上疯狂找购物车按钮。

  • 限制 Agent 的 URL 活动范围（白名单正则）
  • 跳域则自动 page.goBack() 并中断当前动作
  • 最大步数：单个用例最多 15 步，超限立刻请求人工介入
需新建：URLGuard 模块

💥 脏数据污染

现象：Agent 为了跑通提交表单，在真实数据库塞了 100 条垃圾记录，导致依赖特定数据的用例全崩。

  • 探索前调用 reset_environment 或 mock_database 工具
  • Prompt 中严厉警告：严禁修改全局设置
  • 为 Agent 提供沙箱化的测试夹具
部分可行：需设计 Tool 接口

💥 幻觉断言

现象：页面报错"密码错误"，但 Agent 迫于完成任务的压力，脑补出"登录成功"并生成了错误的脚本。

  • 剥夺 Agent 的最终裁判权
  • 探索结果必须附带页面快照 + DOM 节点内容
  • 增加只读的独立复核 Agent 专门做断言验证
需新建：Verifier Agent

6 定位器稳定性金字塔
❌ 弱定位器 — XPath 含 class / DOM 层级 / 动态哈希
⚠ 组合属性 — [type=submit] · button:has-text
▶ 稳定相对定位 — 锚定邻近静态文本
⭐ 语义定位器 — getByRole · getByLabel （推荐首选）
✅ 精确唯一属性 — 静态 id / name
🔴 最高优先级 — data-testid 专属测试属性
// 生成的脚本需包含多层回退：
1st try: page.getByTestId('login-button')
2nd try: page.getByRole('button', {name: '登录'})
3rd try: page.locator('text=登录').locator('..').locator('button')

8 需要你决定的几个设计问题

🔴 Agent 操作页面需要人类确认吗？

当前 agent loop 对 mutation 工具要求用户按 y/n 确认。探索式生成中，每次 click 都要确认会毁掉流畅性。全自动运行又可能翻车不可控。

可能的折衷： 自动模式下允许自由操作，但每一步的快照都保留在轨迹中供事后审计。探索完成后一轮整体 review。

🔴 蒸馏引擎放在哪？

选项 A：放在 teshi-bridge Python sidecar 中，离 CDP 数据最近。
选项 B：放在 Rust agent 模块中，由 LLM 在 agent loop 里做降维。

权衡：A 效率高但跨语言；B 统一但延迟更大。

🔴 teshi-id 的作用域

临时 ID 每次页面加载重新生成？还是持久化基于 XPath 的指纹 ID？前者简单但轨迹无法离线复用。后者复杂但支持更丰富的场景。

建议：第一阶段用临时 ID（最简单），第二阶段蒸馏时再映射到稳定选择器。

🔴 探索模式的入口

在 TUI 中新增一个"探索"Tab？还是在现有 AI 对话中通过浏览器工具隐式调用？前者 UX 清晰但工程量大。后者迭代快但容易混淆。

倾向：先在 AI 聊天中加 browser 工具原型验证，验证成功后独立出专门的探索面板。
